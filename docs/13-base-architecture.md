# 13. Базовая архитектура системы

## Назначение базовой архитектуры

Базовая архитектура описывает основную структуру системы
с учетом бизнес-требований, функциональных и нефункциональных
требований, выбранного архитектурного подхода и ключевых
атрибутов качества.

Для данной системы базовая архитектура должна обеспечить:

- поддержку пользователей по всему миру
- запись и анализ тренировок
- социальные взаимодействия между пользователями
- проведение соревнований и челленджей
- интеграцию с внешними устройствами и системами компании
- защиту пользовательских данных
- возможность постепенного развития платформы

С учетом этих требований в проекте используется
микросервисная архитектура.

---

## Архитектурный подход

В качестве основного архитектурного подхода выбрана
микросервисная архитектура.

Причины выбора:

- разные части системы имеют различную нагрузку
- система должна масштабироваться независимо по сервисам
- компания имеет большой штат разработчиков
- необходимо интегрироваться с внешними системами
- требуется гибкое развитие платформы

Микросервисный подход позволяет разделить систему
на отдельные сервисы, каждый из которых отвечает
за свою функциональную область.

---

## Ограничения и предпосылки

При проектировании архитектуры учитывались следующие
ограничения и предпосылки:

- пользователи могут находиться в разных регионах мира
- соревнования могут создавать резкие скачки нагрузки
- система должна работать с внешними фитнес-устройствами
- необходимо использовать функции смартфона
- требуется интеграция с существующими системами компании
- большая часть инфраструктуры компании уже размещается в облаке
- в компании используется несколько облачных провайдеров
- необходимо уделять особое внимание безопасности данных

Эти ограничения напрямую влияют на выбор архитектурных решений.

---

## Основные архитектурные уровни

Базовую архитектуру системы можно разделить на следующие уровни.

| Уровень | Назначение |
|---|---|
| Клиентский уровень | Взаимодействие пользователей с платформой |
| API-уровень | Единая точка входа и управление доступом |
| Сервисный уровень | Основная бизнес-логика |
| Интеграционный уровень | Взаимодействие с внешними системами |
| Уровень данных | Хранение данных системы |
| Сквозные механизмы | Безопасность, мониторинг, логирование |

---

## Клиентский уровень

Клиентский уровень включает приложения, через которые
пользователи работают с платформой.

Основные компоненты:

- мобильное приложение
- веб-интерфейс

Клиентский уровень позволяет пользователю:

- зарегистрироваться и войти в систему
- управлять профилем
- записывать тренировки
- анализировать свои результаты
- участвовать в соревнованиях
- искать пользователей и группы
- получать уведомления
- получать персонализированные рекомендации

Клиентские приложения также могут использовать функции смартфона,
например GPS, шагомер и другие сенсоры, для автоматической
фиксации тренировок.

---

## API-уровень

На API-уровне располагается API Gateway.

API Gateway выполняет следующие задачи:

- прием запросов от клиентских приложений
- маршрутизация запросов к внутренним сервисам
- централизованная аутентификация и авторизация
- ограничение и контроль доступа
- скрытие внутренней структуры системы от клиентов

Использование API Gateway упрощает работу клиентских приложений
и делает архитектуру более управляемой.

---

## Сервисный уровень

Сервисный уровень содержит основные доменные сервисы системы.

### Identity Service
Отвечает за:

- регистрацию пользователей
- аутентификацию
- управление учетной записью
- настройки приватности

### Workout Service
Отвечает за:

- запись тренировок
- хранение информации о тренировках
- предоставление истории тренировок
- базовую аналитику тренировок

### Social Service
Отвечает за:

- социальные связи между пользователями
- подписки и друзей
- поиск пользователей и групп
- взаимодействие внутри сообществ

### Feed Service
Отвечает за:

- публикацию результатов тренировок
- формирование ленты активности
- отображение социальной активности

### Challenge Service
Отвечает за:

- создание соревнований и челленджей
- учет участия пользователей
- формирование рейтингов
- отображение результатов соревнований

### Notification Service
Отвечает за:

- push-уведомления
- уведомления о комментариях, приглашениях и результатах
- доставку сервисных уведомлений

### Promo Service
Отвечает за:

- персонализированные рекомендации
- промо-предложения
- связь активности пользователя с коммерческими сценариями

---

## Интеграционный уровень

Интеграционный уровень отвечает за работу с внешними
системами и устройствами.

Основной компонент — **Integration Service**.

Он используется для:

- подключения фитнес-устройств
- взаимодействия с Apple Health / Google Fit и аналогичными системами
- получения данных со смартфона
- интеграции с e-commerce системой компании
- взаимодействия с другими внутренними системами компании

Выделение отдельного интеграционного уровня позволяет
изолировать внешние зависимости и не перегружать
доменные сервисы дополнительной логикой.

---

## Уровень данных

Для хранения данных используется подход, при котором
каждый сервис имеет собственное хранилище данных.

Это решение выбрано по следующим причинам:

- снижение связанности сервисов
- независимое развитие и масштабирование
- уменьшение количества конфликтов при изменении данных

Основные типы данных:

| Тип данных | Где используются |
|---|---|
| Данные пользователей | Identity Service |
| Данные тренировок | Workout Service |
| Социальные связи и группы | Social Service |
| Публикации и реакции | Feed Service |
| Данные соревнований | Challenge Service |
| Уведомления | Notification Service |
| Рекомендации и промо | Promo Service |

---

## Сквозные механизмы

Некоторые механизмы являются общими для всей архитектуры.

### Безопасность
В системе используются:

- аутентификация пользователей
- разграничение доступа
- защита API
- шифрование данных при передаче
- защита критичных данных при хранении

### Наблюдаемость
Для сопровождения распределенной системы используются:

- централизованное логирование
- мониторинг сервисов
- сбор метрик
- оповещения о сбоях

### Управление нагрузкой
Для поддержки роста системы предусматриваются:

- горизонтальное масштабирование сервисов
- использование облачной инфраструктуры
- возможность независимого масштабирования наиболее
  нагруженных компонентов
