# 11. Список ADR

В рамках проектирования системы были зафиксированы ключевые
архитектурные решения..
Это позволит связать выбранную архитектуру
с требованиями проекта, атрибутами качества и рисками реализации.

---

## ADR-001. Выбор микросервисной архитектуры

Система должна обслуживать пользователей по всему миру,
поддерживать большое количество участников соревнований,
интегрироваться с внешними устройствами и существующими
системами компании.
Также в компании работает большое количество команд разработки,
что требует возможности параллельного развития различных
частей системы.

Для реализации системы выбрана микросервисная архитектура, данный подход позволит разделить систему
на независимые сервисы, каждый из которых отвечает
за отдельную функциональную область, а также:

- масштабировать отдельные части системы независимо
- упростить развитие системы несколькими командами
- изолировать сложные интеграции
- поддерживать рост системы

Преимущества использования микросервисов:

- высокая масштабируемость
- гибкость развития
- удобство интеграций

Недостатки:

- усложнение инфраструктуры
- необходимость настройки мониторинга и логирования
- повышение сложности взаимодействия сервисов

---

## ADR-002. Использование API Gateway

Клиентские приложения должны взаимодействовать
с большим количеством сервисов, а также необходимо обеспечить единую точку входа в систему,
централизованно решать вопросы маршрутизации,
безопасности и контроля доступа.

Принято решение использовать API Gateway как единую точку входа
для клиентских приложений.

API Gateway позволит:

- скрыть внутреннюю структуру микросервисов
- централизовать аутентификацию и авторизацию
- управлять маршрутизацией запросов
- упростить клиентские приложения

Преимущества использования API Gateway:

- единая точка доступа
- упрощение клиентского взаимодействия
- удобство контроля безопасности

Недостатки:

- появление дополнительного компонента в архитектуре
- необходимость обеспечивать отказоустойчивость gateway

---

## ADR-003. Выделение отдельного Integration Service

Система должна интегрироваться:

- с фитнес-устройствами
- с функциями смартфона
- с внешними сервисами
- с e-commerce системами компании

Интеграции могут использовать разные протоколы
и форматы данных.
Принято решение выделить отдельный Integration Service для работы
с внешними системами и устройствами, что позволит:

- изолировать внешние зависимости
- уменьшить связанность доменных сервисов
- упростить расширение числа интеграций
- локализовать изменения при появлении новых устройств

Преимущества:

- независимое развитие интеграций
- упрощение основной бизнес-логики

Недостатки:

- дополнительный сервис в архитектуре
- необходимость управления преобразованием данных

---

## ADR-004. Разделение системы на доменные сервисы

Система включает различные функциональные области:

- управление пользователями
- тренировки
- социальные функции
- соревнования
- уведомления

Эти области имеют разные сценарии использования
и разную нагрузку.

Решено разделить систему на доменные сервисы:

- Identity Service
- Workout Service
- Social Service
- Challenge Service
- Feed Service
- Notification Service

Что позволит:

- разграничить ответственность компонентов
- проще масштабировать нагруженные части системы
- упростить сопровождение и развитие

Преимущества:

- понятное разделение ответственности
- лучшая масштабируемость
- удобство развития

Недостатки:

- усложнение взаимодействия между сервисами
- необходимость продуманной интеграции и мониторинга

## ADR-005. Использование отдельных хранилищ данных для сервисов

Разные сервисы работают с различными типами данных:

- учетные данные пользователей
- данные тренировок
- социальные связи
- соревнования
- уведомления

Т.к. единая база данных для всех сервисов увеличивает связанность, принято решение: каждый сервис должен иметь собственное хранилище данных.
Это позволит:

- уменьшить связанность сервисов
- упростить независимое развитие
- снизить риск конфликтов между сервисами
- лучше масштабировать хранение данных

Преимущества:

- независимость сервисов
- меньшая связанность
- гибкость развития

Недостатки:

- усложнение обмена данными
- необходимость решать вопросы консистентности

---

## ADR-006. Использование облачной инфраструктуры

Система должна обслуживать пользователей по всему миру,
а нагрузка может существенно изменяться в зависимости
от активности пользователей и соревнований.

Решено развертывать систему в облачной инфраструктуре и это позволит:

- быстро масштабировать ресурсы
- гибко управлять вычислительной мощностью
- использовать управляемые сервисы
- упростить запуск системы в нескольких регионах

Преимущества:

- гибкость масштабирования
- сокращение времени запуска инфраструктуры
- удобство эксплуатации

Недостатки:

- зависимость от облачного провайдера

## ADR-007. Централизованный мониторинг и логирование

Микросервисная архитектура усложняет сопровождение системы,
так как сбои могут происходить в разных компонентах,
а проблемы сложнее локализовать.

Принято решение использовать централизованные механизмы мониторинга,
логирования и сбора метрик, позволяющее:

- быстрее выявлять проблемы
- отслеживать производительность сервисов
- анализировать ошибки
- поддерживать наблюдаемость системы

Преимущества:

- более простая диагностика проблем
- улучшение эксплуатационной поддержки
- повышение надежности системы

Недостатки:

- дополнительные затраты на инфраструктуру наблюдаемости
- необходимость настройки единого стандарта логирования

## ADR-008. Усиленные меры защиты персональных данных

Система работает с персональными данными пользователей,
включая данные о тренировках, геолокации и активности.

Требования безопасности являются критичными, поэтому необходимо использовать усиленные меры защиты данных:

- шифрование данных при передаче
- шифрование критичных данных при хранении
- разграничение доступа
- контроль доступа между сервисами

Такой подход позволит снизить риски:

- утечки данных
- несанкционированного доступа
- нарушения приватности пользователей

Преимущества:

- повышение доверия пользователей
- снижение рисков безопасности
- соответствие требованиям по защите данных

Недостатки:

- дополнительная сложность реализации

---

## ADR-009. Использование асинхронного взаимодействия для части процессов

В системе существуют процессы, которые не требуют
немедленного синхронного ответа пользователю:

- отправка уведомлений
- обработка части интеграций
- обновление ленты активности
- обработка результатов соревнований

Для части процессов решено использовать асинхронное взаимодействие.
Это позволит:

- снизить нагрузку на основные сервисы
- повысить устойчивость системы
- уменьшить время отклика пользовательских операций

Преимущества:

- лучшая производительность
- повышение отказоустойчивости
- более гибкая обработка фоновых задач

Недостатки:

- усложнение архитектуры взаимодействий
- необходимость контроля доставки и обработки событий

## ADR-010. Интеграция с существующими системами компании

В компании уже существуют приложения для покупки товаров,
а также специализированные приложения для отдельных видов спорта.

Для обеспечения повторного использования функциональности
и увеличения продаж необходимо интегрировать новую систему
с существующими решениями.

Принято решение использовать Integration Service
для взаимодействия с внутренними системами компании.

Это позволит:

- повторно использовать существующие сервисы
- обеспечить доступ к каталогу товаров
- реализовать переход пользователей к покупкам
- снизить дублирование функциональности

Преимущества:

- ускорение разработки
- снижение затрат
- интеграция с существующей экосистемой

Недостатки:

- зависимость от существующих систем
- необходимость поддержки совместимости API

## ADR-011. Поддержка мультиоблачной инфраструктуры

В компании используется несколько облачных провайдеров,
и нет единого стандарта размещения систем.

Для соответствия текущей инфраструктуре компании
система должна поддерживать возможность работы
в мультиоблачной среде.

Принято решение проектировать систему с учетом развертывания в разных облачных провайдерах.

Это позволит:

- выбирать оптимальный провайдер под задачи
- снизить зависимость от одного облака
- повысить отказоустойчивость системы

Преимущества:

- гибкость размещения
- снижение рисков vendor lock-in
- возможность оптимизации затрат

Недостатки:

- усложнение инфраструктуры
- необходимость унификации подходов к развертыванию
